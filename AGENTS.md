# digikit: agent instructions

Reverse engineering and emulation of the Elektron Digitakt II and Digitone II, with a ColdFire MCF5441x CPU and SHARC+ DSP, for desktop and browser (Wasm).

Use **DT2 OS 1.17** and **DN2 OS 1.12** for analysis, patches, tests and reported addresses. DN2 1.11 remains a patch port for patchkit; the health proof runs on DN2 1.12 and DT2 1.17. Analysis and reported addresses stay on 1.17/1.12. DT2 1.16 and older images are references only: resolve their addresses on the current image before use. Patchkit anchors resolve by hash through `ports/`.

Start with [README.md](README.md) for setup and the newest `docs/handovers/HANDOVER-*.md` for current work. Detailed guides: [layout](docs/LAYOUT.md), [testing](docs/TESTING.md), [regression acceptance](tests/regression/README.md), [instrumentation](docs/INSTRUMENTATION.md), and [findings index](docs/FINDINGS.md).

## Core rules

- Preserve user work and follow session instructions for branches and commits. Commit verified work at useful breaking points; changes to `main` go through a PR.
- Never commit firmware or derived material: `firmware/*.syx`, `out/`, `apps/web/.local`, card images, or users' sample audio.
- Never name, copy or quote the vendor DSP toolchain or its files. Cite public manuals listed in [SHARC sources](docs/sharc/SOURCES.md).
- Put results in `docs/findings/`, one topic per file, indexed from `docs/FINDINGS.md`; handovers describe ongoing work. Marks: **[V]** verified here, **[D]** measured or read once, **[O]** open, **[C]** corrects an earlier claim. Before marking [V], a second agent must check against image bytes. An empty caller list does not prove dead code.
- Before work likely to take more than a day, state payoff and confidence; recommend stopping when they are weak.
- Device facts come from `devices/*.toml` ([device data](docs/design/device-data.md)); code branches on `[capabilities]`, never on a device name. `lint` runs `tools/nx/device-literals.mjs`, which fails when a file's count of device ids differs from its baseline; after removing literals, run `node tools/nx/device-literals.mjs --write`.
- Use static evidence first. Bound emulator runs with `--limit` or `--seconds`. Stop only your own PIDs or run directories; never use `pkill` or `killall` on emulators.
- For performance claims, give the ceiling first, then one paired A/B using `tools/devtools/coupled_ab.py`. Host instruction ratios (`cpu.dsp_thread_insns_per_audio_s`, `sharc_matrix` `insn_ratios_B_over_A`) repeat within 0.02% on a busy host: use them to judge path-length changes, and keep the paired timing A/B as the final check. `tools/devtools/sharc_cells.py` produces these counts, parity and exit tables for two binaries. A generated-core or transpiler change is compared by giving each label its library: build the B library with `verify_build cores` from the B gen dir (or point at one) and pass `--env B:DIGI_SHARC_CORE_LIB_<DEV>=PATH` to `coupled_ab.py`, `sharc_cells.py` or `sharc_matrix.py run`; without it both labels load the same stored core and the tool prints "both labels use core <key>".

## Checks

Use `mise run test` for complete affected verification and the merge gate. Its device tests are selected by area: the changed paths name areas (`runtime/core/owners.toml` for the runtime crates, `services/<name>` for services; the area tags of the records in `metadata.runtimeAcceptance`), the gate runs the device tests of those areas, the changed projects' own device tests, the fixed `gate-device-smoke` set (cross-service integration) when `affected` selects any device test, and `gate-smoke` and `gate-pins` when their inputs changed; it prints the device halves it skipped. `mise run test -- --all-affected` selects every device test whose key changed (the old default); `test:full` and `test-device-all` run everything. Precise when the area is known, wide when it is not: when any changed path that reaches device tests names no area (a shared or unowned runtime module, the SDK, patchkit, `owners.toml`), the gate runs every affected device test and names the path; a device file widens to that device's halves only; `test-conformance` follows the same rule. Name tags by hand to add: `mise run test:subset -- S:machines C:loading` prints the device tests of those record tags plus `gate-smoke` and `gate-pins` when `affected` selects them, and `--run` runs them ([testing](docs/TESTING.md) "Named device subset").
When selection is unclear, run `mise run test:plan` first: Nx explains the tasks without running them. Conformance targets are selected like device tests (by area, above) in the merge gate, and like every other target elsewhere: `affected` runs the tasks of projects whose declared inputs (including dependency outputs) changed between base and head, and the plan lists them. A task whose inputs did not change does not run. Device test files not listed in `metadata.mergeTests` of the owning project.json key their merge cache on what the test loads (rule below), so a change that reaches them only through shared inputs replays their last result. Merge and narrow keys leave out the driver packages (`packages/dk-session`, `packages/test-support`, `packages/control-client`) that the test imports, except the files that hold device facts (protocol, log layout, emulator launch, key codes; `DRIVER_SUBJECT_FILES`): their host tests cover them and are the proof for driver code; `test-device-all` keeps them in its full key. Keys of `mergeTests` files hold the patched image hashes of their device (`dist/bytes/images-<device>.sha256`), the daemon test key of their device (`dist/bytes/daemon-test-<device>.key`) and the pack verdicts, not the patchkit binary or `dist/daemons.json`; narrow keys hold the same image hashes and daemon key of the device, only the packs the test loads, `dist/bytes/pack-verdicts.json` when it imports `runtime/pack-needs.ts`, and the patchkit key when it is live. Builds key on sources, tests key on what they run: the key of a device or conformance test (merge and narrow) holds only the artifacts the test loads (the image hashes and the daemon test key of its device, `MERGE_BYTES`, and its packs), its own test files and setup, the files its record lists in `sources`, its import closure and `DRIVER_SUBJECT_FILES`; no other source file of the module, its subject or the runtime is an input, so a test that reads a source file at run time must list it in `sources`. The conformance merge key holds the packs, image hashes and patchkit key of the devices, not the patchkit binary. A test that runs patchkit imports `tests/regression/runtime/patchkit.ts`, which puts the patchkit key of its device (`dist/bytes/patchkit-test-<device>.key`, written by `patchkit:cli` from the build's dependency file) in its key and sets `DIGI_PATCHKIT_LIVE` (`runtime/patchkit-exec.ts` refuses to run patchkit in any other Nx task; `pnpm lint` checks it). `test-device-all`, `test-conformance-all` and `stock-all` keep the full key (the full-input form, run on request); the merge targets `test-conformance`, `stock` and `regression:test-device` leave the driver packages out. Each device half keys on the files of its own device only (`tools/nx/device-files.mjs`; a merge half of a test that loads the whole registry keeps all device files): an edit of another device's file, ports or peer file selects no half of this device; the full keys keep them all. `mise run test:full` runs every target with full inputs (`test-device-all`) and runs only when Em asks. Merge gate: `mise run test` plus the static checks (`pnpm nx:pilot run-many -t lint,fmt-check,rust-fmt,typecheck,python-checks`). The default gate already is that subset on DT2 and DN2: the PR quotes the gate's selected and skipped lines.  A stack of PRs shares one subset gate and merges together. `affected` sees git changes only: after a change to untracked inputs (firmware, ready snapshots, override binaries) or to what `tools/nx/device-inputs.mjs` or `coupled-inputs.mjs` hash, run the named targets.
Use the owner's explicit Nx target or named test while iterating. `test:changed` is only cheap preflight,
not complete verification. Do not use `--skip-nx-cache` to rerun a failed test: Nx does not cache failures, and the flag reruns every dependency. Full command details and preparation live in [testing](docs/TESTING.md). Emulator tier settings live in `config/emulator.json`; `tools/emulator/emulator_config.py` and `packages/test-support/src/emulator-config.ts` resolve them.

Test levels: unit tests run without a device. Three layers: unit tests per component own logic and edge cases; assembly tests (`pnpm nx:pilot run core/runtime:test-assembly`, host, seconds) own the seams between separately built real artifacts (per seam one case that fits and one typical refusal; a case that starts to test logic is a unit test); device tests own only what the firmware or hardware shows. Rules: (a) every `test-device` and `test-conformance` target `dependsOn` `test-assembly`; (b) a new service or runtime mechanism adds an assembly case before any device test, and a review asks whether each assertion sits at the lowest layer that can see it; a device test asserts only what the firmware or hardware shows, and its record names that reason; logic in a device test is split into a unit or assembly test, and a change that touches an area splits that area's mixed device tests; device tests prove the integrations a change touches: a change local to one owner runs that owner's device tests, and a change to an input every device test reads runs the device tests of the changed behaviour plus a small smoke set instead of every selected device test ([testing](docs/TESTING.md)); (c) a test's setup files live in its own project, never in inputs that every device test hashes; (d) generated artifacts get host consistency checks (a committed object, ABI word or table against its source) and a build rule rebuilds whatever a changed input feeds; (e) a lane is host-green only when its assembly tests pass ([testing](docs/TESTING.md) "Assembly tests"). A device test runs without the SHARC DSP unless it passes `dsp: 'sharc'` (`resolveDsp` in `packages/test-support/src/session.ts` is the only place that decides): a test needs it for audio, PCM, DSP memory or a machine or effect module's DSP path, and the session throws on `pcm.*`, `dsp.*` and `audio.*` calls without it. The record's `dsp` field only sets the emulator core budget (`DIGI_EMU_DSP`); nothing checks it against the source. Device tests are TypeScript (Vitest) and live with their subject: `modules/<kind>/<author>/<name>/tests/*.device.test.ts` in the owning module or nested test-only project (`core/runtime-tests` for runtime acceptance), registered in that project's `runtimeAcceptance` metadata, which `modules.mjs` reads (modules, aliases, plusdrive). Only stock-firmware oracles (`tests/regression/dt2`, `tests/regression/scenarios`) and the shared harness stay in `tests/regression`; `tests/regression/runtime` holds only shared harness helpers. Tests that cut or tear the store (`upload-faults.device.test.ts`) run only with `DIGIKIT_TIER=full`: `DIGIKIT_TIER=full pnpm nx:pilot run core/runtime-transfer-tests:test-device--upload-faults` ([testing](docs/TESTING.md)). Device tests share their steps through the harness helpers (`expectRuntimeReady`, `rt.ui` for panel inputs and the waits after them (`until: { event | state | drained | ms }`), `rt.listen()` and `events.until(kind, match, { withinMs })` for waits on the runtime log, `pollUntil` for polls; clocks, `poll` and the restart wait live once in `packages/dk-session/src/waits.ts`, `emu-clock.ts` and `DkSession.waitForBoot/waitForRestart` (a session built with `emulatedOptions` or `wb`'s `connectEmu` waits and probes in emulated time), `captureNote`, `drainInputs`, `runtime/fixtures.ts`) instead of local copies. Waits are in emulated time or on firmware state; wall time only guards against a hang. Python tests test Python tools. Python device scenarios remain for the two pluck menu flows and `pages-dyn-pluck` (same folder), and `tests/digikit/scenarios/upload-rust.toml`; `equiv-dyn-pluck` (same folder) is no test, only the input of `tools/devtools/sharc_matrix.py`; the patchkit smoke matrix stays Python (`gate-smoke`, `tools/patchkit/pk_harness.py`). A Python scenario is deleted once its TypeScript port passes on both devices ([ledgers](docs/plans/ledgers/)). Tests must test our behaviour: no tests of third-party behaviour, of constants against themselves, or of exact command argv. Gate checks are commands, not test files. Fixtures (`tests/fixtures/modules`, table in docs/TESTING.md) are DRY: each contract feature has one canonical fixture, shared parts live in one source, and a variant exists only where a test needs a distinct module identity (a thin wrapper or a temporary-root build). Every test layer uses the same fixtures, so a real module needs no device test of its own when fixtures cover its features.

Before merging, run the merge gate above once (`DIGI_GATE_BASE` sets the base for Nx and the Python selector); selection and targets are in [testing](docs/TESTING.md) "Nx gate". Iteration checks and cheap preflight do not replace it. Do not repeat passed checks without a new change or unresolved concern. Run only the tests that the changed files select. When the selection is wider than the change can reach, fix the project inputs and edges (`tools/nx/*.mjs`, `project.json`) instead of running the wide set.

The local `.nx/` cache is per worktree. Module `test-device` and `test-conformance` (and other cached targets) also use the clone's shared remote cache (`tools/nx/remote-cache.mjs`; plain runs and every gate tier read and write when the server answers). Before enabling or changing `cache: true`, inspect `pnpm nx:pilot show target inputs PROJECT:TARGET --json` / `--check PATH`, review source/dependency/output/toolchain/environment coverage, and prove relevant invalidation and output restoration with scoped checks. Native inspection describes declared inputs, not observed read closure. For Cargo targets retain `node tools/nx/cargo-depfiles.mjs`; see [testing](docs/TESTING.md) "Nx cache". The `digi-control:daemons` Nx prerequisite uses `verify_build daemons`, backed by a content-keyed store shared by all worktrees.

Do not run test directories, full tier sweeps, or smoke `--update` across all cells while iterating. Use quick proof modes; the default test owns smoke coverage. Preserve SHARC golden hashes for refactors; explain intentional updates. A PCM pin (`tests/scenarios/*.json`, the device-test `pcmSha256` pins, the rig pins) is set or changed from a numeric report of the captured signal (pitch against the expected note, crest factor, harmonics, level envelope, onset, stereo match), with the WAV kept for listening; never from a hash alone. Claude approves when the report matches what the fixture should produce; a change in how a module sounds goes to Em.

Wait without polling. Run a long command with a long tool timeout, up to 2 hours for a Claude Code session (`BASH_MAX_TIMEOUT_MS`). Claude Code moves it to the background after about 3 minutes and notifies you when it finishes: wait for that notification. Do not wait with `sleep`, `tail` or repeated log reads, and never use `tail -f`. If you stop early, stop what you started.

## Development and analysis

Iterate with `dk:dev` ([testing](docs/TESTING.md) "Fast iteration"), not with harness runs or fresh boots; run the harness once for the proof. Respect the layers in docs/ARCHITECTURE.md; `mise run check:layers`. Prefer existing tooling and shared helpers over custom runners or wrappers. Use fast unit tests for logic and integration tests for real boundaries. New host/device scenarios use TypeScript/Vitest; analysis, decompilation and devtools use Python. Avoid unrelated refactors.

Code layout: one file per concept, named after the noun it owns (`queue.rs` holds `Queue`; its methods are the verbs). `lib.rs` and `mod.rs` hold only the module doc, `mod` lines and `pub use` exports. When one type's behaviour grows, split it by behaviour into a folder of `impl` blocks (`queue/push.rs`, `queue/drain.rs`). A type two owners share gets its own file named after it; no `types.rs`, `utils.rs`, `common.rs`, `helpers.rs` or `misc.rs`. State is private: no `pub` fields; other code changes state through the owner's methods (`pub(crate)` inside a crate). Unit tests sit beside the code (`#[cfg(test)] mod tests;` with `<file>/tests.rs`); crate-wide tests go in `tests/`. A file over about 400 lines usually holds two concepts. C follows the same rule: one `.c` and `.h` pair per concept.

A PR that adds or changes a tool a developer runs documents its use in the tool's owning doc (commands that work from a clean checkout, expected output) and links it from docs/DEVELOPMENT.md.

The desktop UI and the site keep no module-level state: they build an app object at startup and take the Host, `KeyValue`, `BlobStore`, `WorkerFactory` and `WasmSource` as arguments, so a test gives fakes ([DEVELOPMENT.md](docs/DEVELOPMENT.md) "Host and EmuRpc", "The app object", "WorkerFactory"). oxlint fails `invoke` outside `tauri-host.ts` and `localStorage`, `indexedDB` or `new Worker` outside `storage.ts`, `blob-store.ts` and `workers.ts`. Code below the apps (`packages/`, `modules/`, `tests/regression/`, `tools/`) imports no app: oxlint fails an import of `apps/`, `@digi/web` or `@digi/desktop`.

The emulator hosts (`digi-emud`, `coupled-run`, the app) hold no generated SHARC core: each device's core is a library from the shared store, named by `DIGI_SHARC_CORE_LIB_DN2` / `_DT2`. Every launcher (`native_emu.py`, `coupled.py`, `sharc_cells.py`, `verify_build daemons`, Vitest `coreLibEnv`) provides them; for a hand-run host use `uv run python -m tools.devtools.verify_build cores [--env-out FILE]`. Hosts build into the no-core target dir (`node tools/nx/rust-env.mjs -- cargo ...`); use `--gen` only for what links `sharc-gen` (`sharc-core-lib`, unit tests of `sharc-peer` and `sharc-native`, `sharc-rig`, the browser core). A DT2 run reads the region lists with the `_2` suffix (`SHARC_FAST_REGIONS_2`). Details: [emulator README](packages/emulator/README.md) "Core libraries".

Run Python tools from the repository root as `uv run python -m tools.<owner>.<module>`. Import through `tools`; never modify `sys.path`. Child tools use `[sys.executable, "-m", ...]` with `env=tools.python_env()`. Find tasks with `mise tasks` and options with `mise run TASK -- --help`.

Use existing database helpers before one-off queries: `tools/coldfire/cf.py` and `tools/sharc_dev/sharc.py`. Read dumps first. Ghidra uses one JVM per project and language `68000:BE:32:ColdfireEMAC`; check apparent missing callers with `tools/coldfire/refscan.py`.

SHARC instruction semantics belong only in `tools/sharc_dev/sharc_core/`; trace/run tools are drivers. Changes there or in `tools/sharc_dev/sharc_transpile/`, `tools/sharc_dev/sharc_transpile_infer.py`, or `tools/sharc_dev/sharc_rsgen.py` change `CORE_FINGERPRINT` and require costly regeneration. Back up each generated directory, regenerate DN2 and DT2 using `out/native/{dn2,dt2}-audio/gen/PROVENANCE.txt`, and regenerate the shared core with `mise run gen:core`.

Builds and benchmarks use `tools/devtools/benchlock.py`. `coupled_ab.py`, `native_pgo.py`, `sharc_regionbench.py`, `pk_modcheck` and the scenario runner already take the lock, and the Nx launcher (`pnpm nx:pilot`) takes it for heavy task runs; do not wrap them again (it deadlocks). Launcher outputs in `out/native/target/*/pgo-use` are reserved; experiments use another `DIGI_EMU_PGO_VARIANT`.

## Sub-agents and reports

One agent per step with a self-contained brief: branch, files, exact checks, and named device targets (change -> test), never area tags. Resume an agent only for a one-line follow-up; after a rebase or a review round start a fresh agent. Project agents live in `.claude/agents/` (`lane-worker` for implementation lanes, `coder`, `scout`, `reviewer`).

Report contract, at most 200 words: Result (one line); Commits (hashes); Checks (target: pass/fail); Device runs (targets, minutes); Open items. Details belong in commit messages and the PR text. A reviewer reports ranked findings with `file:line` and a failure scenario, at most about 300 words.

Read failures, not logs: use the gate's failure summary or the failing task's error block; never print a whole Nx terminal output or run log.

Wait on firmware events (`packages/dk-session/src/runtime-events.ts`) or emulated time. A flaky timing test is fixed to wait on an event, never given a longer timeout or a retry.

## Worktrees

Use warm lanes (`tools/devtools/lane.sh NAME [BASE]`) for parallel native edits or long measurements; small edits and reading stay in the main tree. Lanes share artifacts and the virtualenv: do not change Python dependencies there. Use a separate dev-server port per lane.
Each lane builds into its own `dist/native-target/` (deleted with the lane; a lane that predates this pays one cold build). Reuse one cargo target per lane: a new target variant name builds cold (10 to 30 minutes), a rebuild takes seconds. Run `cargo check` before a long build. Start a new branch in a warm lane rather than a new lane; a new worktree pays about 25 minutes of cold builds.
