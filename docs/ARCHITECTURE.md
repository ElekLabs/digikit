# Architecture

This file is the reference for the layers (L0 to L4), what each layer may depend on, the interfaces between the runtime, services and modules, and how a new device or firmware version fits. `tools/devtools/layercheck.py` enforces the rules it can check today (`mise run check:layers`).

## Layers

Five layers, L0 to L4, and the port file beside them. The [taxonomy](design/taxonomy.md) defines the terms and card layout. The [repository layout](LAYOUT.md) shows where the layers live.

```
 L4  Content modules (.dkm, loaded from the card)       Apps (digikit-menu)
        │ A: SDK or service-local imports                  │ dkrt_* and UI APIs
 ───────┼──────────────────────────────────────────────────┼─────────
 L3  Versioned services (.dks, loaded at boot)             │
     samples, machines, fx, lfo, shortcuts, project        │
        │ C: SDK and service-only imports                  │
        ▼                         ▲ B: declared callbacks │
 ──────────────────────────────────────────────────────────┴─────────
 L2  Runtime core (patched in)
     boot, selection, safe mode, package graph and admission, loading, registry, DSP
     loading and link, store, settings broker, transport, diagnostics, tick
        │ platform interface
 ───────┼────────────────────────────────────────────────────────────
 L1  Installer, platform adapters and firmware plug-in points (patched in)
     reset and boot entry, UI/MIDI/exception hooks, shared tables,
     firmware-time stubs, DSP link and stock fallbacks
        │ bindings and device facts             Port file (.dkport)
 ───────┼────────────────────────────────────────────────────────────
 L0  Stock firmware and hardware (ColdFire, SHARC, card, USB)
```

- **A, consumer to service.** A content module or another service calls an SDK import or an explicitly declared service-local import. An SDK import can resolve to the core, an image capability or a service export. A local import declares the provider, minimum API version and function names. Services use these declared imports for cross-service calls.
- **B, runtime to service.** The loader checks declarations from `init` against the packed metadata before accepting a provider. A service can register a `ServiceRow` for lifecycle, record handling and DSP work. Other optional facets include exports, hooks, slot fills, resources and diagnostic sinks. Firmware-facing callers enter loaded services through a validated installed hook or a filled slot.
- **C, service to runtime.** The service implementation uses `CoreApi` in `dkrt-abi`. The card wrapper implements it with service-only `dkc_*` imports, while host tests can supply `FakeCore`. `Service` and the C-ABI `ServiceRow` in `dkrt-abi` define the callback boundary. `package/gen_services.rs` reserves a prefix for in-image rows, currently empty, and `package/svc_rows.rs` registers the loaded rows.

The core owns shared mechanisms and safety policy, including admission, hook installation, scheduling, storage, diagnostics and generic settings and reload operations. A service owns its domain policy and state, including the meaning of any records it declares. A static library such as `services/rows` supplies code at build time. It creates no provider identity or managed lifetime. Shared live state, such as reserved descriptor rows, needs an owner even when multiple services use the same library to write it. The menu renders state and sends requests through runtime and UI APIs. It should leave domain decisions and persistence formats with their owners.

A service needs an image capability only where its contract calls for one. `project.dks` and `shortcuts.dks` install hooks from the port file and have no separate image module. Image capabilities can support more than one service. The port file matches the stock firmware hash and supplies firmware names, hook sites and check values. The installer, platform entry points, firmware-time fallback paths and shared tables that stock code needs remain image-owned. A service wrapper can still contain device-specific hook or DSP routines that bind through the port or the image.

- **R2b** moved files into L2 and L3 folders inside the runtime crate.
- **R2c** is done: the interfaces exist with fakes (`FakeCore`, `FakeService`), the shims of R2b are gone, and `check:layers` enforces the arrows (rule 6). What Cargo enforces: `dkrt-abi` cannot see the runtime. What only `check:layers` enforces: that services see only `core_api`. A separate service crate takes the core by reference (`core: &C`, `C: CoreApi`; R9). Exceptions left for R3b and later: the optional `fxpages_info`, `dkpool_*` and `dkpw_*` symbols of the adapters are still declared where they are used; the DSP row table (`DspState`: voice, effect and track rows) is service data inside a core-owned object, because `DKRT_DSP` is read by host tools (`DKRT_REG` likewise); the walkers of `registry.rs` and `dsp/mod.rs` still hold the machine-only tables (`counts`, `types_of`, `free_rows`, `profile`) that R9 and R10 move.
- **R3a** is done: the `Platform` trait (`dkrt-abi`: device profile, block clock, interrupt mask, flush, card block calls, MIDI, OS upgrade flag, soft reset, with `Tasking`, `SamplePool` and `StagedWriter`) and `RealPlatform`, a zero-sized type in `platform.rs`. `platform.rs` is the only runtime file that names `dkfw`, besides `fw.rs` (R10: the implementation of `dkrt_abi::fw::Fw`). The runtime is one image for all devices and holds no device value. The device files give the facts (`[board]`, `[digikit]`, `[capabilities]`), and `patchkit gen` writes them as the data object `dkrt_dev` (struct `DkrtDevice` in `runtime/core/abi.toml`), which patchkit places in `cf.expansion` with the runtime. `rs/dev.rs` is the one private reader of the object; `RealPlatform` fills its `DeviceProfile` from it (cached DDR window, keep RAM, SD host, DSP block cycles, run-time machine types, safe key). A service gets its facts through `DeviceProfile::by_id(core.device_id())`, from the table `abi/src/profiles.rs` that `patchkit gen` writes from the same files. A device without a profile has no DDR window and no run-time types. `FakePlatform` drives the host tests, and the contract table `runtime/core/tests/platform/contract.toml` is checked against it and by `platform-contract.device.test.ts` on the device (rule 7).
- **R3b** is done: the hooks `cf.view.hook.ui_loop`, `cf.rtos.hook.main_os_task` and `cf.midi.hook.rx`, their trampolines and the exception hook install (`dkplat_exc_install`, which `Platform::install_exception_hook` calls every UI pass) are the L1 adapter `core/platform` (`runtime/platform/platform`). Same hook sites, the same stock-byte checks and the same trampoline code as before; the runtime requires the adapter, and the two link by name (the adapter calls `dkrt_tick`, `dkrt_boot`, `dkrt_midi_rx` and `dkrt_exc`), so every image with the runtime has it and `requires` has no cycle. At this stage the runtime still installed the machine page hooks (finding 128). R12 moved them to `machines.dks`.
- **R7** is done: the record kinds, resources and the in-crate services are one table generated from `sdk/sdk.toml` (`gen_services.rs`, `records::`); the core walks a `ServiceTable` of `ServiceRow` function pointers, not a tuple of types; a module emits a record of a generic kind with `dk_record_add`; the `.dkm` header carries a tagged table (needs, uses, keys, and the entries R12 needs); a pure boot planner (`plan.rs`) returns one `Verdict` for each module before anything loads; a service declares its kinds and the runtime compares them with its table. The `lfo` service (`services/lfo`) is the proof: a new kind with no edit to the registry, the collector, the loader or dkneeds. Patchkit needed one line later, when `patchkit records --check` came: the owner map in `packages/patchkit/src/record_rules.rs` names the crate of each service that owns a kind (written by hand, a test fails for an owner without a line). R11 added module states and their reasons (LOADS v2), shown in Transfer and the DIGIKIT menu. R12 later moved service loading to `.dks` files.
- **R9** is built: the `fx` service moved into the crate `dkrt-svc-fx` (`services/fx`), initially linked into the runtime object. Its functions take the core by reference (`core: &C`, `C: CoreApi`: static dispatch, the runtime passes its zero-sized `RealCore`); `Service<C>` methods take it as their first argument, and the service table (`ServiceTable<RealCore>`) holds `&REAL_CORE` and passes it to each call, so `ServiceRow::of::<Fx>` instantiates the fx code once for `RealCore`. `handlers::exports::fx_entry` calls the export `dk_fx_routes_entry` of the fx file, found by name in the loader's export table (an `internal` import of `sdk/sdk.toml`: the runtime calls it, no module can); the guard counts and the machine types of the MODULES reply are the same kind of export of the machines file, and the `Service` trait names no kind. The fx crate has host tests over `FakeCore`. `CoreApi` gained `device_id`. The link queue is the crate `dkrt-link` and `FakeCore` is in `dkrt-test-support` (`runtime/core/{link,test-support}`), so the service crate tests without the runtime. The code is the same up to inlining of the generic functions into the runtime crate (`lto = false`): text 216,286 to 214,994 bytes (-0.6%).
- **R10** is built: the `machines` service moved into the crate `dkrt-svc-machines` (`services/machines`), initially linked into the runtime object, and `layercheck` asserted the layout. The same pattern as R9: `Machines` implements `Service<C>`, its statics (the click state in `pageclick.rs`, `APPLIED` in `records.rs`) are statics of the crate, and no `REAL_CORE` is named in it. Two interfaces carry what the service needed from the runtime. The firmware's parameter page is the trait `dkrt_abi::fw::Fw` (`mode_key_held`, `page_value`, `object`, `object_value`, `store`, `view_track`, `param_code`): the runtime implements it once as `RuntimeFw` (`fw.rs`: the page's vtable slots, the key state, the stock setter), a function that needs it takes `fw: &impl Fw`, and `FakeFw` (`dkrt-test-support`) fakes it. The native page registration of the firmware adapter (`mf_native_*`) is `CoreApi::native_available`, `native_register`, `native_remove` and `native_turn` (`native.rs` of the runtime), because the `Service` methods have a core argument and no `Fw`. The hooks stay in the runtime: `dkrt_page_key` and `dkrt_page_turn` (`handlers.rs`, called from `tramp.s`) are `#[no_mangle]` wrappers that call `pageclick::page_key` and `page_turn` with `&REAL_CORE` and `&RuntimeFw`, and `handlers::exports` has `param_get`, `param_set` and `machine_types_of` (the module list asks it; the old `registry::types_of` and the unused `registry::counts` are gone). The crate has host tests over `FakeCore` and `FakeFw`: the click detector, the parameter rules, the native page checks, and the record checks, `apply`, `remove`, `cap` and the native page record of the service (a machine or page row is written at absolute firmware addresses, which a host cannot reach: the device tests cover it). The code is the same up to inlining of the generic functions into the runtime crate (`objdiff --erase RealCore` reports 34 differences, all in the moved machines code, its service entry points and the hook wrappers); text 215,268 to 216,132 bytes (+0.4%).
- **R12-1** is built: `samples` and `lfo` are crates too (`dkrt-svc-samples`, `dkrt-svc-lfo`), no service is a folder of the runtime crate any more (`layercheck`), and all four crates have one layout (`src/lib.rs`, `records.rs`, `slots.rs` when the service fills slots, `dsp/` when needed, `tests/`). `module:new -- service NAME` writes it from `sdk/templates/service`; `module:check -- service/NAME` runs `patchkit service-check` (layout, at most one exported symbol `dk_module`, declarations equal to `sdk.toml`) and the crate's tests. `CoreApi` gained `host()` (`dkrt_abi::platform::SampleHost`: pool present, files in the store, interrupt mask, the sample storage) for the platform facts `samples` reads; `FakeCore` has a `FakeHost`, a job queue (`job_pump`) and the `dkpool_*` stubs live in `dkrt-test-support`. The page key and turn slot code of `machines` is `slots.rs`.
- **R12** moved services into `.dks` packages. Service-owned ColdFire hooks moved with them, and the SHARC hooks kept resident stubs with service-owned dispatch behind slots. Six services now ship as card packages.

`core/expansion` is the reset-time installer: it runs at reset and copies all patched-in code to its place. `ports/bindings` holds the generated firmware bindings (a library, not a module).

A service file (`.dks`) holds no firmware address and no firmware bytes. It names firmware through `dk_fw_` (an anchor), `dk_exit_` (the end of a hook's site or an `exits` entry of the hook in `ports/fw`), `dk_ret_` (an `rts`), `dk_stock_` (the stock path, called from the hook) and `dk_tail_` imports ([PATCHING.md](PATCHING.md) "Firmware references"). The port file for the device's firmware (the card file `ports/<device>-<version>.dkport` whose `FW` equals the image `fw_id`) resolves them at load: it carries the name table, the hook sites with a stock check value, and the table item `FW` (the first 8 bytes of the stock image's SHA-256). The loader compares `FW` with the `fw_id` entry that `patchkit apply` puts in the image's info table and refuses a port file for another firmware with `E_HOOK_STOCK`. The port file is built from committed data and carries no firmware bytes. The image info tables hold only what the patched image owns: `machines_info` (version 2, 16 words: registry rows and counts, `mf_ensure`, the native page functions, the slot map, the page rows) and `fxpages_info` (version 4: device numbers, value indices and send cells; its former firmware words are 0).

## Service contract and boot

The target minimum core reads card and selection data needed for bootstrap, manages the generic package lifecycle, and maintains health, crash capture and boot-loop recovery. It can boot and recover without any card service. Directory clients and their listing buffers, along with project-specific policy, are optional users of shared primitives. Today the core also implements store scanning, settings brokering and the live reload queue.

The reset installer and platform hooks bring up the runtime before it can read the card. The boot hook (`dkrt_boot`, `boot.rs`) reads the selection and decides safe mode before any package loads. In safe mode no package loads, the installers stay disarmed and resident service entry points keep their stock fallback; the platform and recovery UI still run. In normal mode the boot reads the header table of every selected file, searches the card for the providers of the hard needs the runtime does not meet (`Loader::find_providers`), and hands every selected module to the package manager as a root of `PackageManager::boot`. The package graph decides the order and refuses a module whose need nothing meets, whose need a service meets only at another major version, or that sits on a cycle. The rules of the core (`admission.rs`, asked as `Manifest::admit` in bring-up order before anything of a package is placed) refuse a package whose kind, slot or hook site another package owns, whose key another package has, or whose uses do not fit the capacity of the device (`dkrt-fit` is the shared rule); a refusal is the package's verdict, with its reason and detail words. Placing a `.dks` on the card alone does not select it.

The manager (`dkrt-lifecycle`) builds its graph from the header tables (`RtManifest`), brings every service up before the first module, and takes the selection's modules as pins. A package that is refused (a file that does not check, an import that does not bind, an `init` that fails, a claim that does not fit) is skipped with the packages that need it and the rest continues; a service left with no consumer by a refusal is taken down again. The refusals and the load status they give are in `lifecycle/codes.rs` (the planner's and the loader's codes, unchanged, so Transfer and the menu show the same for the same cause). The boot record, the module states and the log are written afterwards, per module in selection order, from the manager's report (`Rt::boot`). The verdict of a module the manager refused (`lifecycle/rt.rs`, `verdict_of`) is the graph's or the rules' reason (an unmet need, a version, a service that did not come up with its hash, an owner, a key, the capacity); the failure of a step is the module's FAILED state with the loader's code. The services are told which modules stay (`Loader::number_boot_keys`: a module stays when it was admitted and every service it needs is up, and a refused module takes no number) once, when every service has been tried and before the first module is placed (`ProviderHost::services_up`).

A module's package id, its record and its selection index are one number. Each package comes up as place, link, start, claim, install, activate, attach; the records of a module are applied when the module is attached, in one call over the services it needs (`ProviderHost::attach`, `Loader::package_attach`): every row's `apply` in the order of the table, then each record in file order to the row that owns its kind, as the old registry walk did, so that native pages and effect pages take their shared rows in file order. The module's start only keeps its section. The manager passes the services in the order of their callbacks (`ProviderHost::attach_rank`, the position of the row in the table) and detaches with the same list; the host removes in reverse. A module's needs cover the loaded services that own its record kinds (patchkit packs a hard need for each), and the in-crate services are always in the walk. The DSP part of a package with a DSP section comes up over later UI passes, started right after the package is active (`ProviderHost::start_dsp`; the DSP loader reserves for one package at a time); a failed part takes down the closure of its package through the manager (`PackageManager::take_down_closure`, called by `Rt::dsp_step`) and marks the modules that went with it.

The live job (`package/reload/`, steps CHECK, QUIESCE, UNLOAD, LOAD, DSP, DONE; `job.rs` holds the job and `Ops`, `refusal.rs` the generic refusals, `real.rs` the job of the device and `RealOps`, `phase.rs` the reload phase; tests by operation in `reload/tests/`) keeps its steps and its generic refusals (safe mode, an open upload, a busy card, built menus); the refusals of the services come from `can_stop` of the manager (`check_stop`: each service's `teardown_refusal` for every module of the closure). Its UNLOAD first asks whether the module can be taken down whole (`Loader::package_retire_ready`: its file and I/O jobs retired and its DSP rows cleared), so that a busy module answers `E_BUSY` with the manager, the record and the tick untouched, and the job's abort gives the tick back; then it takes the module and its consumers down without any service (`take_down_closure`; services stay up with no consumer until RC2c), and its LOAD reads the new file's header table and loads it through the manager (`Rt::live_load` and `Rt::reload_load` over `PackageManager::load`, which brings up a service the module needs that is not up and asks the rules of the core against the live set). The CHECK of a file (`Loader::reload_check`, `Loader::live_check_load`, `loader/live.rs`) asks the graph about the needs of the new table with the providers the boot found and did not refuse, then the rules of the core over every live module with the new table at its index. A service that no module of the boot needed was not searched for, so a live load that needs it is refused as missing until the next boot (RC2c).

Capacity: the manifest declares no pools yet (RC3). `admission.rs` keeps judging capacity (the fit rule of `dkrt-fit` over the capacity of the device, counted as packages are admitted) and its refusal is the verdict the boot reports; the manager's own fit check (`plan_fit` over the ledger) has nothing to refuse until the packed headers carry pools.

Callback order governs the walk of registered service rows. It is independent of the dependency order used for package initialization. Runtime 0.11.1 adds optional `callback_order` and service-local API metadata. Loaded rows follow any in-image rows, with ascending explicit order and ties broken by service name. Unordered services follow them. Metadata-less copies of the six shipped packages keep their positions through the name fallback in `svc_rows.rs`. Legacy SDK imports keep their existing lookup and inference. Explicit local imports bind to the named provider and require a compatible API version. Transfer checks the runtime minimum for the new metadata.

A local API can add a provider and ColdFire function exports without a central SDK entry. SDK-wide imports and record kinds still use the SDK contract. A provider that registers a row must match the runtime's service ABI. Discovery and admission use bounded tables, with eight provider slots in the search, including the port when needed. Service and port replacement take effect on restart. For the manifest and working provider/consumer example, see [card services with a local API](MODULE-AUTHORING.md#card-services-with-a-local-api).

### Package lifecycle (in progress)

The [runtime contract plan](plans/runtime-contract-and-lifecycle.md) replaces the separate provider and module paths with one lifecycle. Live now (RC2b-1 to RC2b-3a): the boot and the live job's module load, unload and reload run through the manager, and the package graph is the one planner; the old boot loops, `plan.rs`, `take_down`, `needs_hash` and the one-record unload and load paths are deleted. Remaining: the RC2 device tests are split and proven on both devices (RC2b-3b); services reload and unload from the menu, with orphans, in RC2c.

- `dkrt-lifecycle` (`runtime/core/lifecycle`):
  - `PackageGraph` orders packages from their header tables. Services come up before consumers; take-down runs consumers first, then the target, then orphan services that no pin keeps. A package with keys for a record kind (`KEYS`) comes up after the package that declares it (`KINDS`). Cycles and unmet or incompatible needs are refused: built from header tables, the packages of a cycle, a second service of one name and a hard need newer than an API of the core mark those packages alone (`Node::defect`; `bring_up_order` reports it for that package), so the others still load. A need of version 0 is any version; the provider's major version counts only for a consumer that imports the service's own functions (`SERVICE_IMPORTS`); a soft need never refuses its consumer.
  - `PackageManager` runs boot, load, unload, reload, a take-down of a closure without orphans (`take_down_closure`, also the take-down of a failed DSP part, and `check_stop`), a re-read of the manifest (`refresh_graph`) and a retry of a pending take-down. It works over seam traits (placing, linking, calling services, installing, the manifest of header tables) that the runtime implements and host tests fake.
  - The installer interface sends each CPU's entries to its backend and rolls back across both. A package has at most `MAX_ENTRIES` entries: the hook sites the port file lists plus the slots a header table holds.
- The runtime implements the seams in `runtime/core/src/rs/src/package/lifecycle/`: `session.rs` (`Session`: the loader the seams drive, the checked file and the entries of the package that is being brought up, the module paths, the admission state and what a refused package left for the report), `placer.rs`, `linker.rs`, `host.rs`, `install.rs` (the ColdFire and DSP-slot backends of the installers), `manifest.rs`, `rt.rs` (`Rt`: the manager over the seams for the whole run, with the boot's driver and report, the live job's steps and the DSP step; the runtime is built in place in its static, `Rt::init_at`, `Session::init` and `PackageManager::init`, with the graph and the ledger written where they stand, because `Rt` is 8.8 KB and the boot hook shares the firmware's task stack: `dkrt_boot` has the 6.7 KB frame it had before the manager, and the worst boot chain is about 24 KB), and `codes.rs`. They are thin adapters over the steps of the loader (`loader/package.rs`; each call that runs package code sets `BOOT_IDX` for its duration and restores it). `dkrt_load` still loads one file through `load_inner`, which shares those steps. A package id is a loader record: the module of the selection index with that number, or the provider the search found at that position. The host's `activate` follows the install so nothing is public before the entries are in, and `deactivate` undoes it before they are restored. `can_stop` of a module asks every row (an old row's `teardown_refusal`, a provider's `can_stop`) for it (a routed effect refuses). The seams are tested on the host (`loader/tests/seam_tests.rs`, `loader/tests/assembly_tests.rs`; the manager and `Rt` over the packed `local-ping` and `svc-test` fixtures, with a refused service, a failed DSP part, the live job's steps and a ColdFire hook installed and restored, in `loader/tests/manager_assembly_tests.rs`).
- The runtime crate's source folder (`runtime/core/src/rs/src/`) has two sides (RC2s-1 S5; plan: [resident core and system package](plans/resident-core-and-system-package.md), the call list is in [the boundary inventory](plans/rc2s-1-boundary-inventory.md)). The **resident core** stays in the folder itself: `platform.rs`, `dev.rs`, `fw.rs`, `arena.rs`, `boot.rs` (the boot record writers and the level decision), `boot_env.rs`, `selection.rs`, `safe_mode.rs`, `safe_screen.rs`, `fault.rs`, `watch.rs`, `dlog.rs`, `settings.rs`, `storage/`, `hash32.rs`, `state.rs`, `api.rs`, `mailbox.rs`, `tick.rs`, `transport.rs` with `store_cmds.rs` and `admin_cmds.rs` (the 16 resident upload commands, SELECT among them), `io.rs`, `worker.rs`, `aux_task.rs`, `intro.rs`, `speed.rs`, `health.rs`, `report.rs` and `resident_query.rs`, with `hooks.rs` (the resident core's calls into the package) and `resident.rs` and `resident/` (the resident table, below), and `menu_exports.rs` (the menu's `dkrt_scan`, `dkrt_fit`, `dkrt_capacity`, `dkrt_live` and their companions: resident symbols that call through the hooks). The **system package** is `package/`: `lifecycle/`, `loader/`, `reload/`, `handlers.rs` and `handlers/`, `dsp/`, `dsp_stats.rs` (nothing in the DSP hang watch reads it; the hook `dsp_stats_owner_gone` reaches its `owner_gone`), `entry.rs`, `files.rs`, `scan.rs`, `admission.rs`, `collect.rs`, `registry.rs`, `link.rs`, `core_api.rs`, `imports.rs`, `svc_imports.rs`, `svc_rows.rs`, `gen_services.rs`, `invariants.rs`, `settings_overlay.rs`, `settings_reload.rs`, `module_cmds.rs` (MODULES, LOADS and the registered commands), and the files split out of mixed resident files: `boot_steps.rs` (the boot steps of the package: header tables, providers, load), `capacity.rs` (`dkrt_capacity` and `cmd_capacity`), `live_cmds.rs` (the handlers of CAPACITY, RELOAD, RELOAD_STATE, LOAD, UNLOAD) `commands.rs` (the seven package commands, reached through the `command` hooks) and `hooks.rs` (the package's table of hooks and `attach`) and `resident.rs` with `resident/` (the package's facade over the resident table), and `boot_idx.rs` (the selection index of the module that loads, which only the package reads). The pure helpers both sides need are in `dkrt-abi`: `module.rs` (`Module`, `Ctx`, `LOG_NAME`, `PROVIDER_IDX`, `shown_name`), `boot_path.rs` (`path_hash`, `pick_index`), `fw_id.rs` (`image_fw_id`), `store_path.rs` (`last_part_is`), `sha256.rs` (`Sha`), `image.rs` (the parse and checks of a `.dkm` image, which stage 1 needs too), `command.rs` (`Cmd` and its flags), `log.rs` (the log's phases and sink channel), `runtime_state.rs` (`State`, `PackageState` and `runtime_accepts`) and `fn_addr` in `dev_addr.rs`. **Resident to package: hooks (RC2s-1 S6).** `dkrt_abi::hooks::PackageHooks` has one typed entry per crossing (32 entries, grouped by the resident owner that calls them: boot, tick, command, module, menu, diag, settings, provider), each an `Option<unsafe extern "C" fn>` over integers, pointers and `repr(C)` records. `hooks.rs` holds the installed table and gives each entry a typed caller with a documented default; no resident file names `package::` except `lib.rs` (the module list and the `loader` alias below) and `hooks.rs` (`install`, the one call that makes the package's hooks the table every caller reads; host tests attach the package linked into their binary with `attach_package`). `boot::run` gets the hooks from `stage1::start` (below). With no table (a core-only level) the core boots, serves its 16 own commands, answers the menu exports with errors or zeros and writes the hang record with no module attribution. The package's thunks and table are `package/hooks.rs`. Package code takes the device through `dkrt_abi::package_platform::PackagePlatform` (18 required methods: the 17 of the inventory and `sample_path_max`; `blocks_since` is provided), which every resident `Platform` gives by one forwarding impl; the file is not one of the service ABI files, so the ABI word is unchanged. **Package to resident: the resident table (RC2s-1 S7b).** `dkrt_abi::resident::ResidentTable` has one group of `extern "C"` function pointers per resident owner (platform, boot, dlog, store, store_writer, card, settings, arena, selection, worker, io, intro, sdk_files, api, fault, transport, state), the pointers to the resident statics the package reads (`Views`: `DKRT_STATE`, `DKRT_BOOT`, the paths, menus and runtime-version cells) and the addresses of the 37 module imports the resident core serves (`ImportRows`). The table is a header (`magic`, `major`, `minor`, `size`) and one pointer per group; each group is a `Group<T>` that starts with its own size in bytes, so a group can grow at its end. `dkrt_abi::resident::check` is the one compatibility check (`package::resident::install` calls it now, stage 1 will): the magic and the major are equal, the minor is at least the one the package was built against, and every group covers the entries the package uses; the package reads a group only through the `Resident` it returns. A mismatch is a `Refusal`, never a panic: stage 1 asks `check` before it calls the package's entry, logs the refusal (an error event, the text names the reason and the value word holds what was found) and takes the package as incompatible, so the core runs on its own. Appending an entry at the end of a group, or a group at the end of the table, raises the minor; removing, reordering or changing an entry, or changing a shared view, raises the major. The shared views are `PackageState` (the layout of `State` with the arena's own words `free_head`, `lo` and `hi` opaque: the package uses the arena through `ArenaFns`, including its size), `DkrtBootInfo` and the `MAX_MODULES` arrays; their layouts are part of the major version. Where an entry only forwards (`irq_mask`, `has_dsp`, the settings and SDK file calls ...), the table holds the owner's own `extern "C"` function and no thunk. Where a Rust signature cannot cross (`Result`, `Option`, a slice, a tuple) the entry has an out parameter or a pointer and a length. The resident core builds the one table (`resident/`: one file of `extern "C"` thunks per group, and `table.rs`); the package keeps it in `package/resident/table.rs` and has one facade file per group (`package/resident/arena.rs` ...) with the functions under their original names and signatures, `#[inline(always)]`, so package code changes only its path. `TablePlatform` is the package's `PackagePlatform` over the platform group; the host tests install the table with `test_lock`. The package names no resident module: `check:layers` fails on `crate::<resident module>` in `package/`. The import table of the modules (`package/imports.rs`) lists every name once, as the package's own function or as a field of `ImportRows` (its byte offset in the table, read when a module imports it). `BOOT_IDX` is a static of the package (`boot_idx.rs`). Pure code both sides compile (`Sha`, the image checks, `copy`, `Cmd`, `State`) is in `dkrt-abi`. The resident object holds no package code: the package is its own artifact (`[system_package]` of `runtime/core/module.toml`, packed by `patchkit syspkg build` into `digikit/system.dksp`) and stage 1 loads it at boot. `lib.rs` has no glob re-exports, so every use names its owner module. `lib.rs` keeps one private `use package::loader;` for `dkrt_sdk::optional_imports!`, which names `crate::loader::stub_missing`; the layer rule does not count that alias, and the package crate of RC2s-2 has its own `loader` at its root, so the line goes away then.
- **Stage 1: the system package at boot (RC2s-2 step d; `stage1.rs` and `stage1/`).** `boot::run` asks its `BootEnv` for `load_package` before it decides the level (the status is an input of `level::decide`) and for `start_package` once the level runs the package (normal or safe; a core-only boot starts nothing). The device's `load_package` runs `Stage1<StoreSource, ArenaPlacer>` over the staging buffer: it reads `digikit/system.dksp` in sector-aligned chunks, checks the header (magic and format, table version, size) before it places anything, hashes the body while it streams it, and compares the hash at the end; the `PackageStatus` it gives is `Ok`, `Missing`, `Incompatible`, `Damaged` or `Unreadable` (a read error or a store that stays busy; no crash count). The `PackagePlacer` places the body in the package block (`DKRT_PKG`, `PACKAGE_BYTES` = 320 KiB in `abi.toml`, a static of the runtime's bss apart from the 512 KiB module arena; the arena stays whole, and the capacity report has the block as its own `PACKAGE` kind: limit `PACKAGE_BYTES`, used what the package takes, the placer records `BodyHeader::placed_bytes` in `State.package_bytes` when it places the package and clears it when the block is given back; the report reads that word), copies the body there as it is read, and `finish` relocates the image in place (`dkrt_sdk::syspkg::body::relocate`, base = the image's address), clears the bss over the relocation table, flushes both caches and gives the entry address. A body that has no body header, needs more than `PACKAGE_BYTES` (`placed_bytes`; `patchkit syspkg build` refuses it too) or has a relocation outside the image is `Damaged` (core-only), and nothing stays placed. After a placed package, `Stage1::load_checked` (the one function the device's `load_package` calls, so the host test runs the same order) then runs `stage1::accept_table` (`dkrt_abi::resident::check` with the minor the package was built against, the null table included): a refusal is logged with its reason (`log_refusal`), the block is given back (`abandon`) and the package is `Incompatible`. The boot counts itself (`Level::counts_boot`) and consumes the one-shot flag before any package code runs, so a fault or a hang in the package's entry counts toward safe mode and core-only; then it empties the host directory and, unless the level is core-only, fills the core-owned ids (`BootEnv::package_extent`, the block stage 1 placed: no block, no start) and calls `start_package` (the entry `dkpkg_entry` through `call_at` with the resident table; it installs the hooks it returns). A package that gives null hooks (logged as `package: no hooks`) turns the boot core-only with `CORE_INCOMPATIBLE`; that boot stays counted (the entry ran), its stable period clears the count as for any core-only boot no crash caused, and core-only by crashes (counter at `CORE_ONLY_AFTER`) starts no package until the package file is written or RETRY runs, and a core-only boot (by crashes or by a start failure) calls `abandon_package`, which gives the placed block back to the arena. **Host directory:** the package has no symbol in the image, so the resident core owns `DKRT_HOST_DIR` (`host_dir.rs`, `dkrt_abi::host_dir::HostDir`: a magic, the count of ids the core knows, the ready word and one 32-bit address per id; the ids are `[[host_dir]]` of `abi.toml`, append-only, generated to C, `dkrt-sdk`, `packages/dk-session/src/gen_host_dir.ts` and `packages/dkaddrmap/src/gen_host_dir.rs`). Each id has an owner in `abi.toml` (`owner = "package"` or `"core"`, generated as `HOST_PACKAGE_OWNED` and `HOST_CORE_OWNED`): the package fills its own ids at `attach` through the `host_dir` group of the resident table (`package/host_dir.rs`; the group is resident table minor 2, an appended group; the core refuses a package write to a core id), the core fills its own (`PACKAGE_LO`, `PACKAGE_HI`) before it starts the package and writes the directory's `ready` word last, after the package attached; a tool that reads a directory that is not ready finds no package. A core-only boot leaves it empty and not ready. Tools read one resident symbol and follow the address of the id they need (`dkaddrmap::host_dir`, `packages/dk-session/src/host-directory.ts`, `packageSymbol` of the harness); an empty entry reads as "no package loaded". `DkrtBootInfo` stays 256 bytes: `core_cause` took the word that was reserved (`dsp_wait`, always 0). A core-only boot reports `DkrtBootInfo.reason = SAFE_CORE_ONLY` and the cause in `DkrtBootInfo.core_cause` (`CORE_CRASHES`, `CORE_MISSING`, `CORE_INCOMPATIBLE`, `CORE_DAMAGED`, `CORE_UNREADABLE`; the SAFE log event carries it as argument 3). Host tests run `boot::run` over `FakeBootEnv`, whose `start_package` attaches the package linked into the test binary; the real placement of the built artifact is `stage1/tests/assembly_tests.rs` (`arena_top`).
- The loader (`runtime/core/src/rs/src/package/loader/`) is one `Loader` struct in `mod.rs` with one `impl` block per behaviour: `check.rs` (the checks of a file: head, imports, body), `load.rs` (claim a record, place the image, `init`, the end of a load), `commit.rs` (the commit of a file's declarations and the services' records), `unload.rs` (the take-down of a record), `live.rs` (the checks and preparation of a live job), `plan.rs` (the boot plan: captured header tables, provider search, admission, key numbering). The other files are `discover.rs`, `exports.rs`, `image.rs`, `install.rs`, `package.rs`, `port.rs`, `records.rs`, `role.rs` and `seams.rs`.
  - Known gaps until RC3 and RC2c: the services' `module_commit` (check, measure and write of a module's records) still runs for every row in `start`; the manifest has no pools or claims; a provider that no accepted module needs is not tried, so it is not logged (the old boot loaded every provider it found); a module that declares kinds is admitted in selection order, not before the modules with keys for them (a service owns a kind, and patchkit packs the need that orders a module after it).
- `dkrt-fit` holds the `ResourceLedger` next to the fit rule that patchkit and the web app share. A resource is counted capacity declared by a service or the core; consumers claim units; `fits_with` checks a plan without changing anything.
- `dkrt-abi` holds the provider contract (`Provider`, the optional parts, `ProviderRow` with tagged parts). These files are outside `SVC_ABI_FILES`, and no service uses them yet (RC3).
- Settings are data a package describes, not menus it builds (plan section 6.6, RC3).
- Device tests prove the integrations a change touches; a change to an input every device test reads runs the device smoke set ([testing](TESTING.md#device-smoke-set)).
- The boot-effects snapshot (`runtime/core/src/rs/src/package/loader/tests/boot_effects_assembly_tests.rs`, files `runtime/core/src/rs/src/package/loader/tests/snapshots/boot-effects[-errors]-<device>.txt`) records what one standard selection (a machine, an effect, `lfo-shape`, `local-ping-user` with its provider, and `entry-demo`, which has a `fini`) does on the host. The boot is the real `boot::run` over a host `BootEnv`; the reload and live-load jobs are the real reload `Job` over a host `Ops` (`host_boot_env.rs`, `host_ops.rs`). The good scenario boots, then reloads, unloads and live-loads `lfo-shape`, then unloads `entry-demo`. Per phase the file lists the order of the `init` and `fini` calls and the log events, the installer's platform calls, the service rows, the arena blocks, the module states with their codes, the module records and the card sectors, in the order the runtime keeps them. The errors scenario (`boot-effects-errors-<device>.txt`) boots with a damaged module and a damaged service, then runs an unload of a module that is not loaded, a reload and a live load of damaged files, and the safe boots (the record's one-shot flag and the boot counter at its limit). Host pointers are not recorded: an address is `blk<slot>+<offset>` inside a live arena block, `freed:blk<slot>+<offset>` inside a block that went back (only the flush of a failed load, so only the errors files hold `freed:`), a slot word is named by the name hash of its info entry, and any other address fails the test. Not reachable on the host: crash and hang boots (the crash and hang records and the settings and keep records are stubbed), and the DSP. The machine and the effect load without a DSP part and declare nothing: the host runs no module code, and the real declarations need the DSP rows and the registry tables of the image (their builder calls refuse differently from run to run, because the services read host addresses narrowed to 32 bits). Each device and scenario therefore runs in a temporary child process; the 32-bit narrowing goes with the address seam of RC2s-1, and the service statics with RC3. A step that must not change behaviour leaves the files unchanged. A deliberate change rewrites them with `UPDATE_GOLDENS=1 pnpm nx:pilot run core/runtime:test-assembly`, and the PR explains each changed line. The files are inputs of `core/runtime:test-assembly`.

### Choosing an API

The SDK defines shared public contracts and their generated C and Rust bindings and packaging metadata. For example, a module's `dk_fx_routes` builder call comes from `sdk/sdk.toml`. Its implementation and route policy run in `fx.dks`. Add a public SDK import or record definition when the project will maintain its compatibility, bindings and conventions as part of the shared SDK. A provider can support several consumers through its own versioned API.

A service file provides its code to the runtime in one of two forms; the table of services (`ServiceTable`, rows `Row::Service` and `Row::Provider`) holds both, in callback order, until the six shipped services have moved (RC3). The old form is a `ServiceRow` of `impl Service<C>` (static callbacks, declared with `dk_service_declare_row`). The provider form is a `ProviderRow` over an owner object (`dkrt_abi::provider`): a name hash and a list of tagged parts, each a function table with a version (`PartRef`; lifecycle 1, records 2, DSP 3, tick 4, query 5, describe 6; every old callback is a method of exactly one part, `parts.rs`). `service!(Name, "name", &KINDS, parts = [Records, Tick, ...], hooks = [...], fills = [...], exports = ..., tick = f)` emits the tables, the row and the cell `DK_SVC_OWNER` (`Owner<T>` of `dkrt-svc-rt`): the file's `init` makes the instance with `Provider::start_in` (default: `start` moved into the slot; a service with a large state writes it in place) before the declarations; the cell is `.bss` and passes row and instance with `dk_provider_declare_row`; its `fini` runs `Provider::stop(&mut self)` and drops the instance in place. The loader resolves the row at the commit (`ProviderHandle::resolve`: the row and each table must lie in the package image, a part version newer than the core knows is refused with `E_SVC_ABI`), `svc_rows::add` puts it in callback order, and a part the service did not adopt answers with the default of the old method. `attach` is the old `apply` (a provider also hears a consumer without records), `detach` the old `remove`, `can_stop` the old `teardown_refusal`, `reload_done` the old `live_done`; the part `Query` is the resident query entry. The part tables are versioned by `PartRef.version`, so a new callback is a new version of one part and `PROVIDER_ABI` stays 1; the service ABI word (`SVC_ABI`) changed once for RC3, so every `.dks` is rebuilt. The contract suite (`dkrt_test_support::contract`) runs over either form (`contract::<S>` for an old service, `provider_contract::<Recipe>` for a provider, through the part tables of its row); `local-ping` is the provider fixture.

The service crate that others copy is `services/shortcuts`, the first port to the provider form. Its layout: `src/shortcuts.rs` is the owner object (`Shortcuts`: private state, the `Provider` impl in one block, `Ticker` beside it); `src/records.rs` is the `Records` part of the same owner plus the free `validate` that `patchkit records --check` calls (the rule itself is `src/rule.rs`); a concept the owner holds is a file of its own named after the noun (`bindings.rs`, `keys.rs`, `build.rs` for the builder call's collection); `src/lib.rs` has only docs, `mod` and `pub use`; the service file `dks/` has `src/lib.rs` (the `service!` call), `hooks.rs` and `hooks.s`, `builder.rs` for a builder call that must reach the owner (`wrapper = "builder"` in `sdk/sdk.toml`) and the generated `gen_exports.rs`. The owner lives in the file's cell (`DK_SVC_OWNER`); hooks and builder calls reach it with `DK_SVC_OWNER.with(|s| ...)`, and a host test builds it with `Provider::start` over a `FakeCore`, so no test needs a lock. `patchkit service-check` takes the record kinds of a provider from the `&KINDS_<NAME>` argument of `service!`.

`services/samples` is the second port, a provider with the DSP part and no record kind: the owner `Samples` (`src/samples.rs`) holds `Tracks` (the clients' tracks and the table writes of `writes.rs`), the sample-pool adapter `Pool` (`pool.rs`) and the `PeakWindows`, and implements `Provider`, `DspPart` (`check_sections`, `admit`, `claim`, `release`, `loaded`: the track-table record of a module's DSP section) and `Ticker` in one block each. The module's calls (`dk_sample_pool_*`) and the two pool event slots reach it with `DK_SVC_OWNER.with(...)` (`dks/src/glue.rs`) and answer `E_CONTEXT` or drop the event when there is none. The adapter's `dkpool_tick` runs inside `Ticker::tick` and may call `pool_done` and `pool_lost`, which find the owner through the cell again: this aliases the `&mut self` of `tick` and holds only because `tick` touches no state before that call (a test covers the re-entry). `DKRT_SMP_RECORDS` and `DKRT_SMP_CONTROL` stay named statics because device tests read them by symbol; `Tracks::reserve` is their only writer and the logic reads its own copies. The state is made in place (`start_in`: zero bytes plus the few non-zero values), so the 35 kB track core is never copied through the stack.

A service can define a narrower API in its own headers and export it from its `.dks`. The `local-ping` fixture and its consumer illustrate this path. The consumer declares `[[service_import]]` with the provider name, minimum compatible version and symbols. The packer records the hard need, and the loader links only to the matching provider. Card modules use these declared imports or SDK imports.

A patched-in resident app can query an optional card provider through `dkrt_service_query` (runtime 0.11.2). The provider declares one `[[export]]` named `dk_service_query_v1`, and passes its implementation as `query = path::dk_service_query_v1` to `service!`. The glue checks the entry against the fixed C signature `ResidentQueryV1`. Patchkit marks the export as a resident query and adds the 0.11.2 runtime minimum. The loader activates it with its owning provider and withdraws it when the provider is retired. Each call checks the provider identity, compatible version and live entry. The entry stays private to the broker.

The provider owns operation numbers, typed request and reply layouts, validation and status codes. Publish the wrapper with the provider contract and use a new operation number for a changed layout. Operations run synchronously in the UI task, read state without blocking, and must return before any UI or loader work resumes. They cannot recurse, retain the buffers or publish service addresses. `DKRT_E_MISSING` reports an absent provider or facet. The caller chooses the fallback. A runtime change is needed for a new shared mechanism or lifecycle rule. New operations within this query contract add code to their provider and caller.

The menu keeps pending FX route choices and asks the FX provider which routes fit. The typed wrapper is [dk/fx/route-query.h](../sdk/include/dk/fx/route-query.h). The FX provider reads its effect rows and send-slot capacity. Existing `dkrt_fx` enumeration keeps the same layout and returns an empty list when the provider is absent. The menu uses the previous picker rule when an older provider can enumerate effects but lacks the query facet.

| L3 Service | `services/NAME` (module manifest in `dks/`) | `service` (checked by `patchkit service-check`) | Loaded from a `.dks` file | The core through `CoreApi` (interface C) and `dkrt-abi`, other services through declared imports (interface A) |
| L1 Installer | `runtime/platform/expansion` | `installer` | At reset, once | Firmware bindings |
| L1 Firmware bindings | `ports/bindings` | none (not a module) | Never; generated by `patchkit gen` from `ports/fw/` | Anchors |
| L1 Platform or other image module | `runtime/platform/NAME` (except `expansion`), `image-modules/{points,adapters,fixes,proofs}/NAME` | `adapter` | Inside firmware hooks, in the firmware's contexts | Firmware bindings, runtime exports, other adapters' headers |
| L4 App | `runtime/apps/NAME` | `app` | In the task context, called by an adapter | SDK, `dkrt.h`, `dk_ui_core.h` |
| L4 Content module | `modules/<kind>/<author>/<name>`, `tests/fixtures/modules` | none | Loaded at run time from the card (a `.dkm`) | SDK and declared service-local imports |
| SDK contract | `sdk/` | none | Not code that runs; the contract between L4 and L2 and L3 | Nothing |

## Rules

`layercheck` reads manifests, sources and built objects. It builds nothing; for the objects of content modules it asks patchkit where the objects of this tree's sources are stored (`patchkit build --paths`, about 10 s), so a cache entry another worktree built is never read.

1. **Roles.** Manifests under `runtime/`, `services/` and `image-modules/` set `[module].role` according to the table above.
2. **Sources.** Content modules and apps include only their own files and the SDK (`<dk/...>`, `sdk/dsp/contract`). An app may also include `dkrt.h` and `dk_ui_core.h`. Only the runtime (its `platform.rs`, rule 7), the installer and adapters include `dk_fw_*` headers or depend on the `dkfw` crate. C, ColdFire and SHARC assembly (`#include`, `.include`) and Rust (`dkfw`, path dependencies) are checked.
3. **Objects.** The undefined symbols of the built objects of apps and content modules are SDK imports (`sdk/sdk.toml` `[[import]]`), declared service-local imports (`[[service_import]]`), `dkrt_*`, `dk_ui_*`, `dk_app_*` or the SHARC externs the SDK documents. They never name a firmware anchor (`cf.*`, `dsp.*`, `hook.*`, `pk.*`), and `[object.externs]` never maps a symbol to one.
4. **Apps do not patch.** An app has no `[[op]]` and no `[[claim]]`. If an app needs a firmware hook, the adapter that owns that plug-in point installs the hook and calls the app through an optional symbol (`dk_app_*`).
5. **Capabilities cost nothing unused.** A module asks for capabilities; adapters implement them per device. Prefer data (a field an adapter already passes) to a new firmware hook. A hook must cost at most one flag check on a hot path when no loaded module asks for its capability ([capabilities plan](plans/capabilities.md)).

6. **Arrows inside the runtime.** Service implementations live in their own crates and take the core through `CoreApi`. Card wrappers bind service-only imports and declare their callbacks to the loader. `check:layers` checks allowed crate dependencies and test-only fakes, including renamed and target-specific dependencies. Service-specific runtime bridges are confined to `handlers.rs` and the generated registration code.

7. **Platform.** The runtime manifest installs no firmware hooks. The platform adapter installs boot, UI-loop and MIDI hooks, and the machines service owns the source-page key and turn hooks. The runtime's `platform.rs` and `fw.rs` adapt firmware through the platform and firmware traits. Only `rs/dev.rs` reads `dkrt_dev`. Runtime and service code use profiles and capabilities for device values, which come from `devices/*.toml`.

8. **Kind-free core.** Builders, record semantics and machine or effect state belong to services. The core walks generic records and calls the owning row for checks, application and teardown. `patchkit records --check` and the service share the rules for records a module can validate before it loads. Device- and registry-dependent checks run at load. The core owns generic DSP allocation and load state, while services own voice and effect rows, guard counts and diagnostics. See [remaining ownership work](#remaining-ownership-work) for the current bridges and policy seams.

9. **Resident/package boundary** (rules `boundary-hook`, `boundary-table`, `boundary-abi`; [resident core and system package](plans/resident-core-and-system-package.md), section 4). In the runtime crate, resident code is every file outside `package/` and package code is `package/`. Resident code names package code only in `hooks.rs` (the hooks the package fills at entry, and `install`); package code names no resident module: it calls the resident table through its facade `package/resident.rs` and `package/resident/`; a type that crosses the boundary is declared in the abi crate (`dkrt_abi`) and named from there on both sides. Host-test files and every item behind `#[cfg(test)]` are not read. What the rule does not see: the `use package::loader;` alias of `lib.rs`, items inside inline modules and impls (only top-level declarations count as module items), a `#[path]` module outside `lib.rs`, and paths a macro builds. The rules are enforced (`BOUNDARY_ENFORCED = True` in `layercheck.py`, no baseline file). `uv run python -m tools.devtools.layercheck --boundary-report` lists every crossing with counts per rule and file.

`check:layers` enforces the source and object boundaries it can inspect. The assembly and device checks cover declaration and execution behavior.

Exceptions are listed in `layercheck.py` with a reason: `test/registry-demo` patches the firmware itself (it is patchkit's example of a hook).

Run it:

```sh
mise run check:layers          # or: uv run python -m tools.devtools.layercheck
```

Each violation prints `file:line: rule: what is wrong. Instead: what to do.` The gate runs it in `python-checks` (with ruff and mypy) whenever modules, the SDK or the firmware declarations change; `mise run test:changed` runs it too.

## Profiling

Three sources feed one recorder. The Profile pane and the `wb` CLI show the result as one `dk.profile/1` artifact.

```text
 runtime spans (device and emulator)      debug module, SysEx PROFILE_STATE / PROFILE_READ
 cf.profile    (emulator only)            feature cf-profile, run-time toggle, in every workbench build
 sharc.profile (emulator only)            needs a DSP and a separate build (feature sharc-profile)
          |
          v
 recorder (apps/desktop/ui/src/profile-backend.ts)
   one start / stop / reset / read interface per source;
   a source that is missing or fails is reported with its reason
          |
          v
 dkprof (packages/dkprof, dkprof.wasm)
   the dk.profile/1 artifact, naming through the image address maps, the budget;
   shared by the workbench and the `wb` CLI
```

The spans run on hardware and in the emulator through the same debug module and session layer. The two instruction profiles are `cf.profile {enable?}` and `sharc.profile {enable?}` of the control daemon ([CONTROL.md](CONTROL.md)): `enable: true` starts and clears, `false` stops and clears, no argument reads. A firmware reload starts a new emulator; the daemon starts a profile that was on again on the new one and counts the restarts in its answer, so the recorder can say the recording has a gap. The span clock is device data: `span_clock` and `span_clock_hz` in `[digikit]` of each device file name the timer the spans read. Details: [INSTRUMENTATION.md](INSTRUMENTATION.md#profiles).

## Emulator

The emulator ([packages/emulator/README.md](../packages/emulator/README.md)) runs the ColdFire in `elektron-native-boot` and puts everything the main CPU talks to as a second processor behind one boundary, the `Companion` trait of `digi-coupled`. A device file chooses the companion: the SHARC+ session on DT2 and DN2, the peer ColdFire on the Syntakt, and an inert responder (mailbox answers, no audio) when the DSP or the peer is off or absent. `AudioOut` is the one audio path for all of them: the companion pushes its PCM into it, and the player, the tap, the capture and the pacing read from it. The instruction rate is a property of each emulator (`DIGI_CF_IPS`, else the device's rate), not a global. The generated SHARC core is a library that the host loads, so hosts compile without it. Plan and reasons: [emulator-core-split.md](plans/emulator-core-split.md).

## How a new device or firmware version fits

A new firmware version of a known device:

1. Add the anchors to `ports/` (they resolve by hash) and check the declarations in `ports/fw/`.
2. Run `patchkit gen`. The bindings in `ports/bindings` follow.
3. Fix what changed in the adapters. The adapters hide the difference; no SDK header, no content module and no app changes.

A new device:

1. Add the device profile (`devices/NAME.toml`): limits, patch sets, panel, storage and the values the adapters read (`docs/design/device-data.md`).
2. Add its ports and, where its firmware differs, device-specific adapter sources (`src/cf/NAME/`, `src/dsp/NAME.s`) behind the same adapter API.
3. Keep the SDK contract. A content module that builds against the SDK loads on the new device when the runtime reports the contract version.

## Where the device specifics live

| What | Where |
| --- | --- |
| Firmware addresses and hook sites | `ports/` (anchors by hash) |
| Firmware function and structure declarations | `ports/fw/`, generated into `ports/bindings` |
| Limits, patch sets, panel, storage, span clock | `devices/*.toml` (device profiles) |
| Facts the runtime and services read | `dkrt_dev` object (`DkrtDevice`), `DeviceProfile` |
| Code that hooks or wraps firmware | `runtime/platform/*`, `image-modules/*/*`, and the movable hooks in `services/NAME/dks/` |
| The module contract | `sdk/` (device-neutral) |

## Worked example: the UI path

A menu or screen of an app or module goes through these steps:

1. **Module.** A module calls `dk_ui_menu_new`, `dk_ui_text`, `dk_ui_open` and the other calls of `<dk/platform/ui.h>` (`sdk/include/dk/platform/ui.h`). It knows no firmware.
2. **Runtime.** The runtime links the module's imports when it loads the `.dkm`. The `dk_ui_*` calls are `[[import]]` entries of `sdk/sdk.toml` with `requires = "core/ui"`: the runtime's object names them as `optional` symbols, and patchkit resolves them to the functions of `core/ui`, or to 0 when `core/ui` is not in the image. For 0 the runtime hands out a stub that returns the API's failure value (the entry's `absent`: null, -1 or 0, or nothing for a void call), so a module that uses the UI still loads. An app (a core module) links the same symbols directly through patchkit.
3. **Adapter `core/ui`.** `runtime/platform/ui` implements the calls. It builds the firmware's own views (`VerticalMenuView`, list and text views) through the generated bindings (`dk_fw_view.h`, `dk_fw_menu.h`) and keeps their state.
4. **Firmware views.** The firmware draws and handles the keys.

The SETTINGS entry shows the rule for hooks. `core/ui` owns the hook at the end of the SETTINGS list rebuild (`cf.menu.hook.settings_list.tail`). It calls the runtime's `dkrt_ui_settings_rows(settings_menu)`, which asks the system package through the `ui.settings_rows` hook of `PackageHooks` (appended with resident table minor 3; a package built before it, no package, or a null entry leaves the stock menu as it is). The DIGIKIT menu is a C object linked into the package artifact (`[package_part]` of `core/digikit-menu`, `patchkit syspkg build --part`): the hook points at its `dk_app_settings_rows`, which adds the row with `dk_ui_stock_row`. The menu has no hook, no claim and no firmware include, and nothing of it is in the flashed image. Its calls of the runtime are symbols that the package defines (`package/menu_link.rs`): the ones of the resident core go through the `exports` group of the resident table, the ones of `core/ui` through the import table of the package or the same group.

A module with settings sets the `menu` field of its `dk_module` (`void menu(dk_module_ctx *ctx, dk_ui_menu *menu)`; the `.dkm` header carries its address and `DkrtModule.menu` and `DkrtModule.ctx` give it to the app). The MODULES list of `core/digikit-menu` shows SETTINGS... in the side panel of a loaded module that has one, builds a menu once for it (titled with the module's name) and calls `menu` to fill it only when the user opens it. The check mark of the row stays the only on/off of a module; the runtime owns it, and the module owns only its own settings.

**Lifetime rule.** Menus are never freed, so a module that builds menus of its own is never unloaded or reloaded at run time; a module without menus can be loaded, unloaded and reloaded (`runtime/core/src/rs/src/package/reload/`). So every `ctx`, callback and descriptor that a module hands to `<dk/platform/ui.h>` must point at the module's own static data or code, never at the stack, and menus are built when the user opens them, after all modules are loaded. Then no UI pointer outlives the module that owns it.

The same holds for card reads: the INFO page of the menu gets the module header from `dkrt_module_header` of the runtime, which does the card read in its own buffer.
