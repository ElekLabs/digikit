# core/usb-bulk

A vendor bulk interface (interface 2, EP2 OUT and IN, 512-byte packets) added to the firmware's USB MIDI mode, for run-time modules: `usb_bulk_enable`,
`usb_bulk_take`, `usb_bulk_release`, `usb_bulk_send`, `usb_bulk_state`, `usb_bulk_takeover`, `usb_bulk_giveback` and `usb_bulk_ring` (`sdk/sdk.toml`, `sdk/include/dk/platform/usb_bulk.h`). Plan: `docs/plans/usb-fast.md`
section 4; facts: `docs/findings/42-usb-transfer-routes.md` section 4. EP2 IN runs with 64-byte packets and no zero-length termination, like the firmware's EP1 IN, because the controller's TX buffer holds 64 bytes per endpoint and two back-to-back 512-byte IN packets wedged it on the DN2.

- **No firmware patch.** The USB engine is the same code at the same addresses on DT2 1.17 and DN2 1.12. Its port table is RAM: `usb_bulk_enable` checks
  the stock entry 2 (callbacks, length, the 101 descriptor bytes), then writes four words (connect, disconnect, descriptor pointer and length) and
  re-enumerates with the firmware's own stop and restart pair. Not called, nothing is written and USB is stock. Outside USB MIDI mode (USB CONFIG) enable
  prepares the entry only (the next switch to USB MIDI enumerates with interface 2: one enumeration for a take-over) and returns E_STATE until the device is in USB MIDI mode and no
  switch is settling; bit 2 of `usb_bulk_state` shows the wrong mode live. While enabled, the adapter wakes the module's job four times a second (a timer for the module).
- **Take-over** (`docs/plans/usb-fast-takeover.md`): `usb_bulk_takeover` records the original port (USB AUDIO/MIDI, port 5) and a request; `usb_bulk_tick` (UI task, on the runtime's
  `dkrt_poll_add` list from the first take-over call on, also while bulk is not enabled) calls the firmware's mode switch (`cf.usb.fn.mode_switch`) with port 2 at least 50 ms
  later. `usb_bulk_giveback` and the automatic give-back (the disconnect callback, a bus suspend of 0.5 s, 30 s without a transfer or renew) switch back the same way. After each of these switches the adapter holds the firmware's restart for 2 s (counter 60 instead of 30), releases the PHY's line while the controller is stopped (ULPI function control through ULPI_VIEWPORT, written back before the restart; `UB_ULPI_DETACH 0` turns it off), waits for a reply on EP0 or EP1 IN before it switches and 3.5 s between switches, and forces the firmware's restart when USBCMD.RS is still clear 4 s after a switch with VBUS present (`usb_bulk_forced_restarts`). Facts and reasons: `docs/findings/123-usb-takeover.md`. Refused in
  Overbridge. A port change by another route drops the state without a switch. The USB CONFIG setting byte is never written (test: `cf.usb.value.config_mode`). Bit 3 of the state word.
  `UB_ULPI_DETACH` (default 0 since build A, 2026-11-13): 1 parks the PHY through the ULPI viewport during the hold; hardware showed the failed switches are the ones where that viewport access hangs (finding 123).
- **Anchors** (`devices/fw/usb.toml`): the port table, the active port, the USB CONFIG setting byte, the firmware's restart delay counter, connect, disconnect, queue, cancel, dTD allocation, stop, restart and the mode switch.
- **Receive ring**: up to 60 slots of 16 KiB (960 KiB; four 4 KiB pages each: every dTD names all five page pointers) in the uncached alias of DDR, allocated per session with
  the send slots as one block (a 1 MiB block from the firmware's buddy allocator; the tiers are tried 60, 28, 8 slots, so a heap that cannot give 1 MiB gives 512 KiB, then the old 256 KiB block with 8 slots;
  all tiers refused: E_NOMEM, ST_NOMEM, nothing enabled). At most 12 dTDs are queued on EP2 OUT at once (the firmware's pool has 31, 2 are ours for EP2 IN); the completion callback, in the interrupt,
  marks the slot full, queues the next free slot round the ring and wakes the module's I/O job (`dkrt_io_wake`), so the controller keeps receiving while the job writes the card. The job takes the full slots in
  arrival order. No free slot: nothing queued, the host gets NAK. A 64 KiB frame of usb-fast spans five slots, so the ring takes 12 frames (`usb_bulk_ring` reports it). The run-time switch
  (`usb_bulk_ring`, bit 1 of the usb-fast switch mask, default on; `usb_bulk_ring_off` in the emulator test) off: 8 slots, all queued, the old geometry; it is read when the buffers are allocated and at every queueing. Switching it off while buffers are live keeps the block and only stops queueing beyond 8 slots; a session that starts with the switch off allocates the 8-slot block, which is the clean A/B. `usb_bulk_ring` returns bit 0 the switch, bit 1 always set (the SDK stub returns 0 for an adapter without it), bits 8..15 the window, bits 16..23 the slots of the live block.
  **Send**: the bytes are copied into one of two slots and queued on EP2 IN.
- **Reset**: the connect and disconnect callbacks cancel both EP2 queues with a bounded flush (the stock disconnect polls without a bound), drop buffers
  that were full and not taken, and change the reset count of `usb_bulk_state`.
- **USB_SW events** (log kind 44, level info, except STATE at debug level (raise usb-bulk's level with LOGCFG, `dklog level` or the workbench Level menu to see STATE), ENUM_LATE and TIMEOUT at warn level, and GIVEUP at error level with the error flag; the rare always-on `ub.*` notes of MOD_LOG log at warn, the trace `UB_LOG` ones at debug; needs `digikit/debug`): the timeline of one take-over or release, from the accepted request until the host has configured the device (DONE) or 10 s have passed (TIMEOUT). The tick samples the controller once a pass; at most 32 events a switch (STATE stops at 24; DONE, TIMEOUT, GIVEUP and DROPPED always log). FW_SWITCH, HOLD_BEGIN and PHY_PARK are logged after the PHY is parked, with the time and register words stamped right after the firmware's switch. The callbacks that run in the USB interrupt only count and stamp; the tick logs them. Layout of the five words:

  | Word | Content |
  | --- | --- |
  | a0 | bits 0-7 phase, 8-11 target port, 12 direction (0 take-over, 1 release), 13-15 detail (try, result 0 ok / 1 failed, or wait reason 1 guard / 2 in flight), 16-31 switch number (low 16 bits of `usb_bulk_switches`; the number this switch gets) |
  | a1 | ms since the request (callbacks: the stamped time) |
  | a2 | bits 0-15 USBSTS low 16 bits (URI 6, PCI 2, SLI 8), 16 USBCMD.RS, 24-31 last ULPI function control value seen (0xff unknown) |
  | a3 | PORTSC (callbacks: the copy taken in the interrupt) |
  | a4 | bit 0 OTGSC.BSV, 1 FRINDEX changed since the previous sample, 2 EP3 TX active (ENDPTSTAT or ENDPTPRIME bit 19), 3 clk (USB timer GPT0, GPTIMER0CTL bits 23:0, moved since the previous sample), 8-14 DEVICEADDR.USBADR, 16-21 endpoint enables (EP1 RX, EP1 TX, EP2 RX, EP2 TX, EP3 RX, EP3 TX), 24-31 connect callback count (low 8 bits) |

  REQ detail 4 marks a firmware or menu switch: the active port changed without a request of ours (the stock USB CONFIG menu calls the firmware's mode switch itself; seen when no claimed switch, request or open window exists). The window opens when the tick sees the change (the firmware has stopped the controller by then), target = the new active port, direction 0 if that port is 2, else 1; no FW_SWITCH is logged, and RS_UP (after the firmware's own restart about 1 s later), CONNECT_CB, ADDRESSED, CONFIGURED, DONE, ENUM_LATE and TIMEOUT work as for our switches. Such a window is logged but never recovered: no RECOVERY, reset or wake-up, no GIVEUP.

  Phases: 1 REQ, 2 WAIT (once; the switch is due but the guard or a reply in flight holds it), 3 FW_SWITCH (the firmware's mode switch returned), 4 DISCONNECT_CB, 5 HOLD_BEGIN, 6 PHY_PARK, 7 PHY_RESTORE, 8 RS_UP (USBCMD.RS is 1 again after the stop), 9 CONNECT_CB, 10 ADDRESSED (RS_UP seen, a bus reset seen since the switch (connect callback, URI, or USBADR 0) and USBADR non-zero; detail = the signal that first showed the reset: 1 connect callback, 2 USBSTS.URI, 3 USBADR seen 0), 11 CONFIGURED (an EP1 enable after ADDRESSED of an earlier pass, with the EP1 enables seen 0 since the switch), 12 STATE (a sampled word changed and no milestone fired), 13 ENUM_LATE (no ADDRESSED 3 s after RS_UP; stale state from before the switch cannot satisfy ADDRESSED or CONFIGURED), 14 RECOVERY (detail: try), 15 GIVEUP, 16 DONE (a1: total ms; detail 1: 2 s after ADDRESSED without CONFIGURED), 17 TIMEOUT, 18 DROPPED (a pending request ended without a switch: the mode changed or a give-back came during the take-over delay; closes the window), 19 PHY_BUSY (warn level; the PHY park was refused: detail 0 at the first refusal of a switch, 3 the hold ended without a park; a2 bits 0-7 `usb_bulk_phy_why`, 8-15 tries so far, 16 USBCMD.RS, 24-31 last function control; a3 the raw ULPI_VIEWPORT), 20 PHY_ID (info; once per boot, logged right after the first successful PHY park (controller stopped; never while it runs, the firmware's viewport watchdog would reset it on a hung run): ULPI registers 0 to 3; a2 = vendor ID (reg 1 << 8 | reg 0), a3 = product ID (reg 3 << 8 | reg 2), a1 = 0; detail 0 ok; a refused read is retried at the next park, and after 50 refused tries detail 1 is logged once (the words hold what was read); the emulator's PHY registers are plain storage), 21 PHY_WAKE (info; the ULPI wake-up after a controller reset, see the watchdog; detail 0 WU cleared, 1 timed out with WU still set, 2 RUN was set so no wake-up; a2 = ULPI_VIEWPORT after the poll, a3 = ms polled, a4 with the clk bit). PHY_PARK detail: 0 ok, 1 refused, 2 late ok (a2 bits 8-15 = tries). A refused park is retried once a pass while the hold lasts, but not in the last 100 ms (the restore time). A release in USB MIDI mode without a switch (taken from USB MIDI) logs nothing.
- **ENUM_LATE watchdog**: ENUM_LATE (USBCMD.RS is 1 but no host addressed the device 3 s after RS_UP; detail 1: SOF was seen since RS_UP, the link is alive, no recovery) starts a recovery, at most 2 a switch (`usb_bulk_enum_recoveries`), only when no SOF was seen and no reply is in flight: the tick logs RECOVERY (detail = try), then calls the firmware's stop with restart type 2 (`usb_fw_reset_stop`, anchor `cf.usb.fn.reset_stop`) with interrupts masked. The firmware's tick resets the controller 30 ticks later (USBCMD.RST), initialises it and starts it if VBUS is present: this is the firmware's own reset of a hung USB block (its viewport watchdog uses it). The adapter does nothing else: no PHY access, no own hold, and never the firmware's restart (it sets restart type 1, a plain restart). Why: on hardware a link whose PHY had gone to line state SE0 after a stop stayed dead through a plain stop, a 2 s hold and restart (and a replug); only a power cycle healed it, and the controller reset is the closest thing the firmware has. A recovery starts only when the firmware's restart counter (`cf.usb.value.restart_delay`) is 0. Once RS shows 1 again the adapter checks that the four words of port entry 2 are still ours and writes them back if the firmware's init changed them (note `ub.rehook` at warn level; its value has bit n set for each word n that differed). The recovery does not arm the forced restart of `recovery_tick`. The timeline window goes on (RS_UP, ADDRESSED and ENUM_LATE can fire again; the window ends 10 s after the reset call); a third ENUM_LATE logs GIVEUP, and a TIMEOUT after a recovery logs GIVEUP too. It needs VBUS, takes the switch guard like a switch (no switch number), and does not run while a request, a switch or a hold is pending, or when the active port is no longer the switch's target. RECOVERY always logs (not counted in the 32 events). At most 2 resets a boot in all (the gate is `usb_bulk_enum_recoveries`, never cleared): the firmware's init registers its USB tick in one of 16 shared timer slots each time and nothing frees it (finding 123). Past the cap an ENUM_LATE without SOF logs GIVEUP for the switch and, once a boot, the note `ub.reset.cap` (warn; value = resets made). Only a failed release (target port 5) is reset: the reset zero-fills the dTD pool that the bulk endpoint uses, so a failed take-over (target port 2) logs GIVEUP at that point and, once a boot, the note `ub.reset.take` (warn) until the adapter can rebuild its bulk state first.
- **Wake-up after the reset**: the firmware's USB init clears MISCCR.USBSRC (bit 0 = 0: USB_CLKIN drives the USB clocks, RM 10.3.4). With the ULPI PHY, USB_CLKIN is the PHY's 60 MHz output, so a PHY that stopped its clock leaves the controller without clock: after a reset OTGSC.BSV stayed 0 and the controller never restarted. The clk bit (a4 bit 3) shows whether the USB timer GPT0 counts. Once per recovery, 1500 ms after the reset call, if RS is 0, BSV is 0 and clk is 0, the tick does the ULPI wake-up (RM 24.3.4.12): only when ULPI_VIEWPORT RUN is clear (else PHY_WAKE detail 2), it writes WU (bit 31, RUN clear, port 0) with one 32-bit store and polls until WU clears for at most 15 ms, interrupts not masked (PHY_WAKE detail 0 ok, 1 timed out). WU and RUN are never set together. After a wake-up that worked, if BSV shows within 2000 ms but RS stays 0 for 1000 ms, the adapter calls `usb_fw_restart` once (the restart counter is 0 then, so the firmware starts the controller at once); otherwise the firmware's own BSV interrupt starts it. The sampler goes on as after any reset (RS_UP, ADDRESSED, DONE, or ENUM_LATE and the next recovery or GIVEUP). The emulator does not model GPT0 (clk stays 0) and keeps BSV 1 after USBCMD.RST, so this path is not taken there.
- **Emulator**: FRINDEX is not modelled, so the SOF bit (a4 bit 1) stays 0 there (the FRINDEX read is still a register read per sample); DEVICEADDR and ENDPTCTRL1 to 3 store what the guest writes. The controller is not modelled, except that ULPI_VIEWPORT completes at once (so PHY_BUSY cannot be produced there) and `usb.phy` (`docs/CONTROL.md`) lists the PHY accesses, USBCMD.RS changes and USBCMD.RST writes (a reset completes at once, clears RS and resets DEVICEADDR, ENDPTCTRL1 to 3 and the other registers listed there). `usb.bulk.in` and `usb.bulk.out` (`docs/CONTROL.md`) complete the dTDs through the guest's own callbacks.
  Test: `tests/usb-bulk.device.test.ts` with the fixture `test/usb-echo`.
